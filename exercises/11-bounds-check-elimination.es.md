# Eliminación de Bounds Checks

> **¿Quieres saber más?** Las comprobaciones se generan en `boundsCheck`, en [`cmd/compile/internal/ssagen/ssa.go`](https://github.com/golang/go/blob/go1.27.0/src/cmd/compile/internal/ssagen/ssa.go), y las elimina el pase `prove` de [`cmd/compile/internal/ssa/prove.go`](https://github.com/golang/go/blob/go1.27.0/src/cmd/compile/internal/ssa/prove.go). El pase de depuración `check_bce` está en [`checkbce.go`](https://github.com/golang/go/blob/go1.27.0/src/cmd/compile/internal/ssa/checkbce.go), y los propios tests del compilador en [`test/prove.go`](https://github.com/golang/go/blob/go1.27.0/test/prove.go) son el mejor catálogo de lo que `prove` puede y no puede hacer. El [artículo sobre BCE de Go101](https://go101.org/optimizations/5-bce.html) tiene muchos más patrones.

Go es seguro en memoria: `s[i]` nunca lee más allá del final de `s`. Esa seguridad no es gratis. Antes de cada expresión de índice o de slice, el compilador inserta una comparación y un salto a un panic: un bounds check. El propio compilador elimina la mayoría de estas comprobaciones cuando puede demostrar que son innecesarias. En este módulo aprendemos a ver las que sobreviven, y a escribir código que el compilador pueda demostrar seguro.

## Objetivos de Aprendizaje

Al terminar este módulo:

- Sabrás en qué se compila un bounds check y cuánto cuesta en una CPU moderna
- Entenderás cómo el pase `prove` de SSA elimina las comprobaciones redundantes demostrables
- Listarás las comprobaciones que quedan con `-gcflags=-d=ssa/check_bce/debug=1`
- Aplicarás las pistas habituales: re-slicing, comprobar primero el índice más alto, recorrer con range el slice que indexas
- Conocerás la trampa de que `s[:n]` comprueba la capacidad
- Sabrás cuándo importa eliminar comprobaciones, y cuándo no

## El Concepto: Comprobaciones, y Cómo Demostrar que Sobran

### Qué es una comprobación

Cuando el compilador construye el SSA de `b[i]`, `boundsCheck` (en `cmd/compile/internal/ssagen/ssa.go`) emite un valor `IsInBounds` y un salto:

```go
cmp = s.newValue2(ssa.OpIsInBounds, types.Types[types.TBOOL], idx, len)
...
b.Kind = ssa.BlockIf
b.SetControl(cmp)
b.Likely = ssa.BranchLikely
b.AddEdgeTo(bNext)
b.AddEdgeTo(bPanic)
```

Las expresiones de slice como `b[i:j]` reciben un `IsSliceInBounds`. El bloque de panic llama a `runtime.panicBounds`, un stub en ensamblador que averigua qué comprobación falló y construye el conocido error `index out of range [5] with length 5`. En amd64, cada comprobación se convierte en dos instrucciones:

```
CMPQ    BX, DI                    // compara el índice con len
JLS     panic                     // salta a runtime.panicBounds si está fuera de rango
```

El salto se marca como *probablemente* no tomado, así que el código del panic va al final de la función, y el branch predictor de la CPU aprende enseguida que nunca se toma. Una sola comprobación no cuesta casi nada. **Muchas comprobaciones en un bucle ajustado** siguen costando instrucciones que decodificar, puertos de ejecución y registros para guardar los índices calculados, y pueden hacer que el cuerpo del bucle sea más largo que el trabajo que hace.

### El pase prove

Después de construir el SSA, el compilador ejecuta el pase `prove`. Del comentario al principio de `func prove`:

```go
// prove removes redundant BlockIf branches that can be inferred
// from previous dominating comparisons.
//
// By far, the most common redundant pair are generated by bounds checking.
```

![El pase prove recoge hechos sobre índices y longitudes y elimina las comprobaciones que puede demostrar que siempre están en rango](images/11-prove.webp)

`prove` mantiene una tabla de **hechos** que se cumplen en cada bloque: `i < len(s)` porque estamos dentro de `for i := range s`, `len(b) >= 16` porque estamos dentro de `if len(b) >= 16`, `i >= 0` porque `i` empezó en 0 y solo crece (detecta *variables de inducción* con `findIndVar`). Si los hechos implican que una comprobación siempre pasa, el salto se elimina.

Puedes verlo trabajar con `-d=ssa/prove/debug=1`, que imprime `Proved IsInBounds` por cada comprobación que elimina. En la práctica es más útil la pregunta contraria: **¿qué comprobaciones quedan?**

```bash
go build -gcflags='-d=ssa/check_bce/debug=1' ./tupaquete
```

El pase `check bce` se ejecuta tarde, después de `prove` y del resto de optimizaciones, e imprime cada `IsInBounds`/`IsSliceInBounds` que ha sobrevivido. Cada línea es una comprobación que se ejecuta en tiempo de ejecución.

### Enseñando al compilador

`prove` solo sabe lo que puede ver. Hay patrones que entiende bien:

| Patrón | Por qué funciona |
|---|---|
| `for i := range s { s[i] }` | `0 <= i < len(s)` por construcción |
| `for len(b) >= 4 { b[0] .. b[3]; b = b[4:] }` | la condición del bucle es un hecho sobre `len(b)` |
| `_ = b[7]` antes de `b[0] .. b[7]` | si `b[7]` pasó, `len(b) > 7`, así que los índices constantes menores son seguros |
| `a = a[:len(b)]` antes de `for i := range b { a[i] }` | `len(a) == len(b)` |
| indexar un array `[256]T` con un `byte` | un `byte` siempre es `< 256` |

El tercero se usa por toda la librería estándar. De `encoding/binary`:

```go
func (littleEndian) Uint64(b []byte) uint64 {
	_ = b[7] // bounds check hint to compiler; see golang.org/issue/14808
	return uint64(b[0]) | uint64(b[1])<<8 | uint64(b[2])<<16 | uint64(b[3])<<24 |
		uint64(b[4])<<32 | uint64(b[5])<<40 | uint64(b[6])<<48 | uint64(b[7])<<56
}
```

Sin la pista, se comprueba `b[0]`, después `b[1]` (saber que `len(b) > 0` no te dice que `len(b) > 1`), y así sucesivamente: ocho comprobaciones. Con ella, una.

Lo que `prove` **no** entiende suele sorprender. `for i := 0; i+16 <= len(b); i += 16 { b[i+15] }` parece obviamente seguro, pero `i+16` podría desbordar en teoría, y el compilador no va a suponer que no lo hace. Cada `b[i+k]` tiene su propia comprobación.

> **Desactivar las comprobaciones.** `-gcflags=-B` desactiva por completo los bounds checks. Nunca lo uses en producción, porque elimina la seguridad de memoria, pero es un experimento estupendo: te dice lo *máximo* que podrías ganar con BCE en una función concreta.

|---|---|---|

### Paso 3: Arréglalo

Edita `labs/11-bounds-check-elimination/after.go`:

1. **`SumOrdersAfter`**: sustituye el bucle con índice por un bucle con re-slicing: `for len(b) >= RecordSize { ... b[0] ... b[15] ...; b = b[RecordSize:] }`. Dentro del bucle, la condición es un hecho sobre `len(b)`, así que todos los índices constantes quedan demostrados.
2. **`BlendAfter`**: haz re-slicing de los cuatro slices a longitud `n` **antes** del bucle, y después `for i := range dst`. Ahora `len(dst) == len(a) == len(b) == len(c)` e `i < len(dst)`.

Ejecuta `go test ./11-bounds-check-elimination/`. Lo más probable es que el segundo test falle. Sigue leyendo.

### La trampa de la capacidad

`a[:n]` se comprueba contra **`cap(a)`, no contra `len(a)`**: hacer re-slicing hasta la capacidad es Go válido. Si alguien pasa un slice de 5 elementos con capacidad 10 y `n = 10`, `BlendBefore` hace panic en `c[5]`, pero `c = c[:10]` funciona sin quejarse y tu función lee memoria antigua más allá del final. `TestBlendShortSlicePanics` comprueba exactamente eso. La solución es comprobar tú mismo las longitudes, una vez, antes del re-slicing:

```go
if n > len(dst) || n > len(a) || n > len(b) || n > len(c) {
	panic("BlendAfter: slice shorter than n")
}
dst, a, b, c = dst[:n], a[:n], b[:n], c[:n]
for i := range dst {
	dst[i] = a[i]*3 + b[i]*5 + c[i]
}
```

Vuelve a listar las comprobaciones de la solución:

```bash
go build -tags solution -gcflags='-d=ssa/check_bce/debug=1' ./11-bounds-check-elimination/ 2>&1 | grep solution.go
```

```
11-bounds-check-elimination/solution.go:36:20: Found IsSliceInBounds
```

De 20 comprobaciones dentro de bucles a una sola, fuera del bucle. `SumOrdersAfter` no tiene ninguna.

## Entendiendo los Resultados

**SumOrders es 2,6 veces más rápido** sin cambiar lo que calcula el bucle. El cuerpo del bucle es diminuto: cinco cargas (combinadas a partir de 16 lecturas de bytes), un test, una multiplicación y unas pocas sumas. Las 16 comprobaciones añadían a cada registro 16 cálculos de índice, 16 comparaciones y 16 saltos: más instrucciones que el trabajo real. Este es el bucle caliente completo de la solución, sacado de `go build -gcflags=-S`:

```
MOVL    (AX), SI        // id
MOVL    12(AX), DI      // ts
ADDQ    DI, SI
ADDQ    $-16, CX        // b = b[16:] ...
MOVQ    CX, DI
NEGQ    DI
SARQ    $63, DI
ANDL    $16, DI
XORQ    SI, DX
ADDQ    DI, AX
ADDQ    $-16, BX
CMPQ    BX, $16         // len(b) >= 16
JLT     done
MOVWLZX 10(AX), SI      // flags
TESTW   $1, SI
...
```

Ni una sola comprobación. La secuencia `NEGQ/SARQ/ANDL` es el coste propio del re-slicing: cuando `b[16:]` deja un slice de capacidad cero, el compilador evita crear un puntero más allá del final del objeto (ver el comentario sobre `Slicemask` en `ssagen/ssa.go`). Por eso compilar `before.go` con `-B` (sin ninguna comprobación) fue aún más rápido en nuestras pruebas, 1,42 µs: el re-slicing te lleva casi todo el camino, pero no todo.

**Blend es 2 veces más rápido.** Se han quitado cuatro comprobaciones por elemento de un bucle que hace dos multiplicaciones y dos sumas. Los 1,647 µs para 4096 elementos son unos 0,40 ns por elemento: ahora el bucle está limitado por las propias cargas y escrituras.

> **Sé honesto contigo mismo con BCE.** Estos bucles se eligieron porque hacen muy poco trabajo por comprobación. En un bucle que hace trabajo real por elemento (un acceso a un map, una llamada a función, un fallo de caché), las mismas comprobaciones se pierden en el ruido. También probamos la pista `_ = p[7]` en un parser de cabeceras de 8 bytes dentro de un bucle sobre `[][]byte`: dependiendo de detalles sin relación del código del benchmark, iba desde 2 veces más rápido hasta ninguna diferencia medible. Cuando las comprobaciones no son lo que limita el bucle, quitarlas no aporta nada, y pequeños efectos de layout en el código generado pueden ser mayores que el efecto que estás midiendo. **Usa `check_bce` para encontrar comprobaciones en bucles calientes que un perfil ya te haya señalado**, y mide. No vayas sembrando `_ = b[n]` por todas partes.

## Puntos Clave

- Cada expresión de índice y de slice empieza con un bounds check: una comparación y un salto predicho hacia `runtime.panicBounds`
- El pase `prove` de SSA elimina las comprobaciones que puede demostrar redundantes a partir de condiciones dominantes y variables de inducción
- `-gcflags=-d=ssa/check_bce/debug=1` lista las comprobaciones que han sobrevivido
- Pistas que funcionan: `for i := range s`, `for len(b) >= k { ...; b = b[k:] }`, `_ = b[max]` primero, re-slicing a una longitud común antes de un bucle
- `s[:n]` se comprueba contra la **capacidad**: comprueba las longitudes explícitamente cuando dependas de ellas para la seguridad
- BCE importa en bucles ajustados con poco trabajo por comprobación; en el resto, la predicción de saltos hace que las comprobaciones sean casi gratis
