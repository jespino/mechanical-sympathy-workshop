# Bounds Check Elimination

> **Want to learn more?** The checks are generated in `boundsCheck` in [`cmd/compile/internal/ssagen/ssa.go`](https://github.com/golang/go/blob/go1.27.0/src/cmd/compile/internal/ssagen/ssa.go) and removed by the `prove` pass in [`cmd/compile/internal/ssa/prove.go`](https://github.com/golang/go/blob/go1.27.0/src/cmd/compile/internal/ssa/prove.go). The `check_bce` debug pass is in [`checkbce.go`](https://github.com/golang/go/blob/go1.27.0/src/cmd/compile/internal/ssa/checkbce.go), and the compiler's own tests in [`test/prove.go`](https://github.com/golang/go/blob/go1.27.0/test/prove.go) are the best catalog of what `prove` can and can't do. Go101's [BCE article](https://go101.org/optimizations/5-bce.html) has many more patterns.

Go is memory safe: `s[i]` never reads past the end of `s`. That safety isn't free. Before every index and slice expression, the compiler inserts a comparison and a branch to a panic. Most of these checks are removed again by the compiler when it can prove they're unnecessary. In this module we learn to see the checks that survive, and to write code in a way the compiler can prove safe.

## Learning Objectives

By the end of this module, you will:

- Know what a bounds check compiles to, and what it costs on a modern CPU
- Understand how the SSA `prove` pass removes provably redundant checks
- List the remaining checks with `-gcflags=-d=ssa/check_bce/debug=1`
- Apply the common hints: re-slicing, checking the largest index first, ranging over the slice you index
- Know the `s[:n]`-checks-capacity gotcha
- Know when removing checks matters, and when it doesn't

## The Concept: Checks, and Proving Them Away

### What a check is

When the compiler builds SSA for `b[i]`, `boundsCheck` (in `cmd/compile/internal/ssagen/ssa.go`) emits an `IsInBounds` value and a branch:

```go
cmp = s.newValue2(ssa.OpIsInBounds, types.Types[types.TBOOL], idx, len)
...
b.Kind = ssa.BlockIf
b.SetControl(cmp)
b.Likely = ssa.BranchLikely
b.AddEdgeTo(bNext)
b.AddEdgeTo(bPanic)
```

Slice expressions like `b[i:j]` get an `IsSliceInBounds` instead. The panic block calls `runtime.panicBounds`, an assembly stub that decodes which check failed and builds the familiar `index out of range [5] with length 5` error. On amd64, each check becomes two instructions:

```
CMPQ    BX, DI                    // compare index with len
JLS     panic                     // jump to runtime.panicBounds if out of range
```

The branch is marked *likely* not taken, so the panic code goes to the end of the function, and the CPU's branch predictor learns quickly that it's never taken. A single check costs almost nothing. **Many checks in a tight loop** still cost instructions to decode, execution ports, and registers to hold the computed indexes, and they can make the loop body longer than the work it does.

### The prove pass

After building SSA, the compiler runs the `prove` pass. From the comment at the top of `func prove`:

```go
// prove removes redundant BlockIf branches that can be inferred
// from previous dominating comparisons.
//
// By far, the most common redundant pair are generated by bounds checking.
```

![The prove pass collects facts about indexes and lengths and removes the checks it can prove are always in bounds](images/11-prove.webp)

`prove` keeps a table of **facts** that hold in each block: `i < len(s)` because we're inside `for i := range s`, `len(b) >= 16` because we're inside `if len(b) >= 16`, `i >= 0` because `i` started at 0 and only grows (it detects *induction variables* with `findIndVar`). If the facts imply that a check always passes, the branch is removed.

You can watch it work with `-d=ssa/prove/debug=1`, which prints `Proved IsInBounds` for every check it removes. More useful in practice is the opposite question: **which checks are left?**

```bash
go build -gcflags='-d=ssa/check_bce/debug=1' ./yourpkg
```

The `check bce` pass runs late, after `prove` and the other optimizations, and prints every `IsInBounds`/`IsSliceInBounds` that survived. Each line is a check that runs at runtime.

### Teaching the compiler

`prove` only knows what it can see. Some patterns it understands well:

| Pattern | Why it works |
|---|---|
| `for i := range s { s[i] }` | `0 <= i < len(s)` by construction |
| `for len(b) >= 4 { b[0] .. b[3]; b = b[4:] }` | the loop condition is a fact about `len(b)` |
| `_ = b[7]` before `b[0] .. b[7]` | once `b[7]` passed, `len(b) > 7`, so smaller constant indexes are safe |
| `a = a[:len(b)]` before `for i := range b { a[i] }` | `len(a) == len(b)` |
| indexing a `[256]T` array with a `byte` | a `byte` is always `< 256` |

The third one is used all over the standard library. From `encoding/binary`:

```go
func (littleEndian) Uint64(b []byte) uint64 {
	_ = b[7] // bounds check hint to compiler; see golang.org/issue/14808
	return uint64(b[0]) | uint64(b[1])<<8 | uint64(b[2])<<16 | uint64(b[3])<<24 |
		uint64(b[4])<<32 | uint64(b[5])<<40 | uint64(b[6])<<48 | uint64(b[7])<<56
}
```

Without the hint, `b[0]` is checked, then `b[1]` (knowing `len(b) > 0` doesn't tell you `len(b) > 1`), and so on: eight checks. With it, one.

What `prove` does **not** understand is often surprising. `for i := 0; i+16 <= len(b); i += 16 { b[i+15] }` looks obviously safe, but `i+16` could overflow in theory, and the compiler won't assume it doesn't. Every `b[i+k]` gets its own check.

> **Disabling the checks.** `-gcflags=-B` turns off bounds checking entirely. Never ship that, since it removes the memory safety, but it's a great experiment: it tells you the *most* you could gain from BCE in a given function.

### Step 3: Fix it

Edit `labs/11-bounds-check-elimination/after.go`:

1. **`SumOrdersAfter`**: replace the index loop with a re-slicing loop: `for len(b) >= RecordSize { ... b[0] ... b[15] ...; b = b[RecordSize:] }`. Inside the loop, the loop condition is a fact about `len(b)`, so all the constant indexes are proven.
2. **`BlendAfter`**: re-slice all four slices to length `n` **before** the loop, then `for i := range dst`. Now `len(dst) == len(a) == len(b) == len(c)` and `i < len(dst)`.

Run `go test ./11-bounds-check-elimination/`. The second test will probably fail. Read on.

### The capacity gotcha

`a[:n]` is checked against **`cap(a)`, not `len(a)`**: re-slicing up to the capacity is legal Go. If a caller passes a 5-element slice with capacity 10 and `n = 10`, `BlendBefore` panics on `c[5]`, but `c = c[:10]` silently succeeds and your function reads stale memory past the end. `TestBlendShortSlicePanics` checks exactly that. The fix is to check the lengths yourself, once, before re-slicing:

```go
if n > len(dst) || n > len(a) || n > len(b) || n > len(c) {
	panic("BlendAfter: slice shorter than n")
}
dst, a, b, c = dst[:n], a[:n], b[:n], c[:n]
for i := range dst {
	dst[i] = a[i]*3 + b[i]*5 + c[i]
}
```

Re-run the check listing on the solution:

```bash
go build -tags solution -gcflags='-d=ssa/check_bce/debug=1' ./11-bounds-check-elimination/ 2>&1 | grep solution.go
```

```
11-bounds-check-elimination/solution.go:36:20: Found IsSliceInBounds
```

From 20 checks inside loops to a single one, outside the loop. `SumOrdersAfter` has none at all.

## Understanding the Results

**SumOrders is 2.6x faster** without changing what the loop computes. The loop body is tiny: five loads (combined from 16 byte reads), a test, a multiply and a few adds. The 16 checks added 16 index computations, 16 compares and 16 branches to every record, more instructions than the real work. Here is the whole hot loop of the solution, from `go build -gcflags=-S`:

```
MOVL    (AX), SI        // id
MOVL    12(AX), DI      // ts
ADDQ    DI, SI
ADDQ    $-16, CX        // b = b[16:] ...
MOVQ    CX, DI
NEGQ    DI
SARQ    $63, DI
ANDL    $16, DI
XORQ    SI, DX
ADDQ    DI, AX
ADDQ    $-16, BX
CMPQ    BX, $16         // len(b) >= 16
JLT     done
MOVWLZX 10(AX), SI      // flags
TESTW   $1, SI
...
```

Not a single check. The `NEGQ/SARQ/ANDL` sequence is the re-slice's own cost: when `b[16:]` leaves a zero-capacity slice, the compiler avoids creating a pointer past the end of the object (see the `Slicemask` comment in `ssagen/ssa.go`). That's why compiling `before.go` with `-B` (no checks at all) ran even faster in our tests, at 1.42 µs: re-slicing gets you most of the way, not all of it.

**Blend is 2x faster.** Four checks per element were removed from a loop that does two multiplies and two adds. The 1.647 µs for 4096 elements is about 0.40 ns per element: the loop is now limited by the loads and stores themselves.

> **Be honest with yourself about BCE.** These loops were chosen because they do very little work per check. In a loop that does real work per element (a map lookup, a function call, a cache miss), the same checks are lost in the noise. We also tried the `_ = p[7]` hint on an 8-byte header parser in a loop over `[][]byte`: depending on unrelated details of the surrounding benchmark code, it was anywhere from 2x faster to no measurable difference. When the checks aren't what limits the loop, removing them buys nothing, and small layout effects in the generated code can be bigger than the effect you're measuring. **Use `check_bce` to find checks in hot loops that a profile already pointed you to**, and measure. Don't sprinkle `_ = b[n]` everywhere.

## Key Takeaways

- Every index and slice expression starts with a bounds check: a compare and a predicted branch to `runtime.panicBounds`
- The SSA `prove` pass removes checks it can prove redundant from dominating conditions and induction variables
- `-gcflags=-d=ssa/check_bce/debug=1` lists the checks that survived
- Hints that work: `for i := range s`, `for len(b) >= k { ...; b = b[k:] }`, `_ = b[max]` first, re-slicing to a common length before a loop
- `s[:n]` is checked against **capacity**: check lengths explicitly when you rely on them for safety
- BCE matters in tight loops with little work per check; elsewhere, branch prediction makes checks nearly free
